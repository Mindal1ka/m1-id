# M1 ID

> **Твій MyStat — таким, яким він має бути.** Єдиний акаунт, красива PWA, усі функції справжнього
> додатка і жодної зайвої кнопки.

Робоча назва **M1 ID** (легко змінити). Це повноцінна платформа: власна система
акаунтів + підключення акаунтів MyStat (mystat.itstep.org) + єдина single-page PWA,
у якій працюють *усі* розділи оригіналу — розклад, домашка, оцінки, магазин, харчування,
клуби, нагороди, чат — але в зручному й красивому інтерфейсі.

Проєкт побудований поверх глибокого реверсу справжнього API: повний опис — у
[`MYSTAT_API.md`](../MYSTAT_API.md), жива OpenAPI-спека мок-сервера — [`openapi.json`](./openapi.json).

## 💡 Візія

Оригінальний MyStat — великий Angular-застосунок із 98 лінивими чанками, трьома сокетами та
162 ендпоінтами API. Ми робимо **свій клієнт**, який:

- 🎨 **Красивіший**: темна тема, плавні анімації, продуманий UX замість legacy-Angular.
- ⚡ **Швидший**: PWA — миттєвий запуск з домашнього екрана, офлайн-режим на кеші,
  агресивний prefetch під час синхронізації.
- 🔑 **Зручніший**: один акаунт M1 ID → всередині можна підключити один або кілька
  акаунтів MyStat (наприклад, кілька дітей) і перемикатися між ними миттєво.
- 🧠 **Розумніший**: бекенд знає все про API з OpenAPI-спеки і не хардкодить жодного шляху —
  при зміні API достатньо оновити спеку.

## 🏗 Архітектура

```
┌─────────────────────────────┐         ┌──────────────────────────────┐
│   ФРОНТЕНД (SvelteKit PWA)  │         │   БЕКЕНД (FastAPI, Python)   │
│                             │         │                              │
│  • M1 ID: реєстрація/вхід   │  HTTPS  │  • /auth/*     — M1 ID JWT   │
│  • Онбординг-анімація       │◄───────►│  • /accounts/* — прив'язка   │
│  • Single-page застосунок   │  JSON   │  • /sync/*     — збір даних  │
│  • Service Worker, офлайн   │         │  • /api/mystat/* — універс.  │
│  • IndexedDB кеш            │         │    проксі за спекою openapi  │
│  • i18n (ua/ru)             │         │  • SpecRegistry (openapi.json)│
└─────────────────────────────┘         └──────────────┬───────────────┘
                                                       │ Bearer <JWT MyStat>
                                                       ▼
                                        ┌──────────────────────────────┐
                                        │  mapi.itstep.org/v1/mystat/… │
                                        │  + файловий сервіс fsx*.     │
                                        │  + notify/log/chat socket.io │
                                        └──────────────────────────────┘
```

**Усі запити до MyStat ідуть через наш бекенд.** Клієнт ніколи не тримає токен MyStat:
він зберігає лише сесійний JWT M1 ID, а бекенд підставляє справжній `Authorization:
Bearer <access_token>` + `X-Language` / `X-UserId`, коли ходить у mapi.

Чому так:

| Прямі запити з браузера | Через наш бекенд ✅ |
|---|---|
| CORS непередбачуваний (прод віддає його лише своєму фронту) | CORS контролюємо ми |
| Токен лежить у localStorage клієнта — XSS вкраде | Токен зашифрований у нашій БД |
| Не можна кешувати/агрегувати | Кеш, агрегати, офлайн-снапшоти |
| Пароль MyStat потрібен на клієнті | Логін виконує сервер |

## 🧩 Ключовий принцип: Spec-Driven Backend

> **Жодного захардкодженого шляху до MyStat у коді.**

При старті бекенд завантажує `openapi.json` і будує **SpecRegistry**:

```python
class SpecRegistry:
    """Читає OpenAPI-спеку і перетворює її на карту можливостей."""

    # path → {method → Operation}
    # Operation: operationId, tags, parameters, requestBodySchema, security
```

Що це дає:

1. **Універсальний проксі** `ANY /api/mystat/{path}`:
   - перевіряє, що шлях+метод існують у спеці (інакше одразу 404 — як справжній mapi);
   - валідує query/body проти схем із `components.schemas`
     (`LoginIn`, `EvaluateLessonIn`, `CreateOrderIn`, …);
   - підставляє `{branch_alias}` у шаблони шляхів (`/v1/mystat/{branch_alias}/homework/list`);
   - проксує запит у mapi з потрібними заголовками й віддає відповідь як є
     (включно з пагінацією заголовками `X-Pagination-*`).
2. **Самоопис для фронта**: фронт теж читає спеку → типізований API-клієнт
   генерується з `openapi.json` (жодних ручних типів).
3. **Живучість**: якщо MyStat оновиться — оновили спеку, код не чіпали.
4. **Довідник прямо в застосунку**: розділ «Про API» малюється з тієї ж спеки
   (теги, операції, маркери чесності 🟢✅⚠️❌ з описів).

Знання, яких немає в спеці (сокети, енами статусів ДЗ `1/2/3/5`, два різні ID,
особливості пагінації), живуть в одному місці — `backend/app/knowledge.py` — і
підтверджені документом [`MYSTAT_API.md`](../MYSTAT_API.md).

```

```

```
  ├─ успіх   → зберегти в кеш (spec_cache/openapi.json), завантажити в SpecRegistry
  ├─ недоступний → взяти останній кеш

      і hot-reload за mtime файлу кешу.
```

Таким чином спека завжди свіжа, а система деградує м'яко.

## 🔐 M1 ID — власна система акаунтів

### Реєстрація
Користувач створює єдиний акаунт: **логін + пароль + e-mail**.

- Пароль → хеш **Argon2id** (ніколи не зберігається у відкритому вигляді).
- E-mail → верифікація листом (код/посилання) — на MVP допускаємо «soft-check».
- Після реєстрації/входу клієнт отримує **свій JWT M1 ID** (коротке життя +
  refresh), який використовується для всіх запитів до нашого бекенда.

### Підключення акаунта MyStat
В основному меню — «Додати акаунт MyStat»:

1. Користувач вводить **логін і пароль від MyStat** (ті самі, що в оригінальному застосунку).
2. Наш бекенд виконує `POST https://mapi.itstep.org/v1/mystat/auth/login`
   → отримує JWT access_token (живе рівно 30 днів).
3. Токен **шифрується** (AES-256-GCM, ключ сервера з env) і зберігається в БД разом
   із метаданими акаунта (branch_alias, ім'я, фото, logbook_id ≠ id_user_storage!).
4. Запускається онбординг-анімація (див. нижче), поки бекенд збирає всі дані.
5. Готово — користувач усередині PWA.

### Токен MyStat: стратегія без пароля (вирішено)

Пароль від MyStat **не зберігаємо взагалі** — лише access_token (зашифрований).

Життєвий цикл токена (ланцюжок з оригінального клієнта, §2 MYSTAT_API.md):

```
запит до mapi → 401?
├─ ні    → ок
└─ так   → POST /auth/refresh {} → новий JWT («ревок» старого)
           ├─ успіх → зберегти новий зашифрований токен, повторити вихідний запит
           └─ невдача (токен відкликаний остаточно / минув 30 днів)
                → account.status = needs_relogin
                → застосунок м'яко просить повторний вхід в акаунт MyStat
                  (користувач вводить логін/пароль один раз — як в оригіналі)
```

Жодних «просимо перелогінитися раз на місяць» на рівному місці: користувач бачить
повторний вхід **лише якщо refresh не зумів урятувати токен**.

## ✨ Флоу першого входу (онбординг + анімація)

Після введення логіна/пароля MyStat користувач бачить повноекранну анімацію,
поки йде первинна синхронізація:

```
        Привіт 👋                Ми готуємо все для вас..           Майже готово...
   ┌────────────────┐          ┌────────────────────────┐        ┌─────────────────┐
   │  login → JWT   │  →  паралельний збір усіх даних  →  │ збірка снапшота │→ PWA
   └────────────────┘          └────────────────────────┘        └─────────────────┘
```

Етапи технічно:

| Крок | Що відбувається | Повідомлення |
|---|---|---|
| 0 | `POST /accounts/link` → бекенд логініться в MyStat | «Привіт» |
| 1 | `POST /accounts/{id}/sync?full=1` запускає конвеєр | «Ми готуємо все для вас..» |
| 2 | Паралельно тягнуться: `auth/me`, `config`, `page-counters`, `gaming/get-balances`, `schedule/get-month`, `homework/list` (усі статуси), `statistic/*`, `profile/get-personal-data`, `payment/*`, `news`, `custom-awards/*`, `file-token`, … | прогрес-бар за групами |
| 3 | Відповіді складаються в кеш (БД + клієнтський IndexedDB) | «Майже готово...» |
| 4 | Редірект у застосунок, дані вже на екрані | — |

Анімація: Svelte transitions + Lottie/CSS, прогрес приходить по SSE
(`GET /sync/events`) — жодних «висячих» екранів.

Повідомлення анімації — мовою акаунта (за замовчуванням українська, як в оригіналі).

## 🔄 Рушій синхронізації даних

**Sync Engine** — серце бекенда. Описується декларативно, списком задач,
кожна задача = виклик зі SpecRegistry:

```python
SYNC_PLAN = [
    Task("profile",  ["auth_me"],            critical=True),
    Task("core",     ["branch_config", "page_counters", "gaming_balances"]),
    Task("study",    ["schedule_month", "homework_all_statuses", "statistic_marks",
                      "statistic_attendance", "statistic_progress"]),
    Task("money",    ["payment_history", "payment_next", "balances"]),
    Task("fun",      ["custom_awards_items", "awards_balance", "shop_products"]),
]
```

- **Повна синхронізація** — при прив'язці акаунта й за кнопкою «Оновити все».
- **Інкрементальна** — точкові запити при відкритті розділу (fresh-first),
  фоновий refresh за розкладом.
- Усе, що можна віддати з кешу — віддається миттєво, мережа наздоганяє у фоні
  (stale-while-revalidate на рівні нашого API).

## 🖥 Фронтенд: SvelteKit + PWA

| Рішення | Вибір |
|---|---|
| Фреймворк | **SvelteKit** (SPA-mode, adapter-static) |
| Стан | Svelte stores + context; серверні дані через свій легкий шар (SWR-патерн) |
| API-клієнт | генерується з `openapi.json` (openapi-typescript) → повний автокомпліт і типи |
| PWA | Service Worker (Workbox): precache app-shell, runtime-cache API, offline-fallback |
| Офлайн-кеш | IndexedDB (Dexie) — снапшоти розділів, переживає перезавантаження без мережі |
| Анімації | svelte/transition, view-transitions API, скелетони замість спінерів |
| Іконки/жести | bottom-nav + свайпи, pull-to-refresh, install-prompt |
| Тема | темна за замовчуванням + світла, CSS custom properties |
| i18n | paraglide/typesafe-i18n: **українська за замовчуванням**, словник оригіналу
`examples/i18n-uk.json` як база; додавання нової мови = один файл локалі |

### Екрани (single-page, вкладки)

```
┌──────────┬──────────┬──────────┬──────────┬──────────┐
│  Головна │ Розклад  │ Домашка  │ Оцінки   │  Ще …    │  ← bottom navigation
└──────────┴──────────┴──────────┴──────────┴──────────┘
«Ще»: профіль, оплата, магазин, харчування, клуби, нагороди, чат, новини,
налаштування, перемикання акаунтів, довідка по API.
```

Кожен розділ — **робочий**, не «кнопка показати JSON»:
- Розклад: тиждень/місяць, кольори за предметами, позначки відвідування, відео уроків.
- Домашка: таби «До виконання / На перевірці / Виконано / Ретейк», здача файлів (≤25 МБ).
- Оцінки: середні за предметами, динаміка, лідерборд, «зірковість» тижня.
- Магазин/харчування/клуби: кошик, замовлення, баланси, QR їдальні.
- Нагороди батьків + аватар за бобра: покупка/екіпірування предметів.
- Чат: список бесід, повідомлення (реалтайм через наш WS-релей).

### Єдиний стиль відповідей: Normalizer (не просто проксі!)

Бекенд — це **шлюз-структуризатор**: кожна відповідь MyStat приводиться до одного
зручного конверта, щоб фронт ніколи не розбирав 10 різних форматів.

```
{
  "ok": true,
  "data": { … },            # корисне навантаження (нормалізоване)
  "meta": {                 # єдина пагінація/лічильники (з _meta АБО X-Pagination-* АБО Laravel-стилю)
    "page": 1, "perPage": 20, "total": 114, "totalPages": 6
  },
  "error": null | [{ "field": "…", "message": "…" }]   # як в оригіналі
}
```

Шари нормалізації:

1. **Envelope** — завжди (успіх/помилка/пагінація в одному вигляді).
2. **Пер-роздільні нормалізатори** (`services/normalizers/`) — лагодять відомі
   примхи з MYSTAT_API.md:
   - `homework/list?status=5` приходить **масивом секцій** → розгортаємо в плаский список + meta;
   - статуси ДЗ `1|2|3|5` → строкові enum'и для фронта (`done/examination/pending/retake`);
   - пагінація з заголовків `X-Pagination-*`, з `_meta` і «голa» → один `meta`;
   - баланси гейміфікації `[...] за alias` → об'єкт `{cristals, coins, achivements}`;
   - два ID (`logbook_id` ≠ `id_user_storage`) пробрасуються явно і не плутаються.
3. **Pass-through** — усе незнайоме проходить без втрат (ніколи не викидаємо поля).

Нормалізатор прив'язується до операції **за operationId зі спеки** — тобто теж
spec-driven: немає операції в реєстрі нормалізаторів → чистий pass-through усередині конверта.
Фронт отримує передбачуваний `{ok, data, meta, error}` на кожен чих.

### Контракт API

```
ANY /api/mystat/{path}
  ?__account=<id>              # який підключений акаунт використати
  ?__branch=<alias>            # override branch (інакше з профілю токена)
  body/query — як у справжньому API, валідується за спекою

Відповідь: конверт {ok, data, meta, error} + HTTP-статус дзеркалить зміст вихідного.
401 від mapi → refresh-ланцюжок (див. «Стратегія без пароля») → при провалі
клієнт отримує код ACCOUNT_NEEDS_RELOGIN і показує м'який повторний вхід.
```

## 🗄 Модель даних БД

```sql
users               # M1 ID
  id · username UNIQUE · email UNIQUE · password_hash (argon2id)
  created_at · email_verified_at · settings_json

mystat_accounts     # підключені акаунти MyStat
  id · user_id → users · label
  branch_alias · logbook_id · id_user_storage · fio · photo_url
  access_token_enc  (AES-256-GCM)          # пароль НЕ зберігаємо — лише токен
  token_expires_at · status: active|needs_relogin|disabled
  last_synced_at

snapshots           # кеш відповідей для офлайну та швидкості
  id · account_id · section · payload_json · fetched_at
  UNIQUE(account_id, section)

sessions            # refresh-токени M1 ID
  id · user_id · expires_at · revoked_at
```

SQLite на старті → PostgreSQL на проді (SQLAlchemy дозволяє змінити один рядок конфіга).

## 🛡 Безпека

- **Ніколи** не комітимо токени/паролі (див. сумний досвід `token.txt` — тримати поза git!).
- Паролі: Argon2id (наші) + TLS до всіх зовнішніх викликів.
- Токени MyStat: AES-256-GCM, ключ `TOKEN_ENC_KEY` лише в env сервера.
- Сесія клієнта: короткоживучий JWT M1 ID в httpOnly cookie + refresh з ротацією.
- Rate-limit на `/auth/*` і `/accounts/*/link`.
- **E-mail верифікація без SMTP-листів**: синтаксис (RFC) + DNS MX-запис домену
  (dnspython — «ящик фізично може отримувати пошту») + блоклист одноразових
  доменів. Опційно пізніше — активна SMTP-проба RCPT TO.
- Логи не містять Authorization-заголовків і тіл з паролями (фільтр у middleware).
- Мінімальні права: бекенд робить у MyStat лише те, що попросив користувач.

## 📡 Реалтайм: сокети

Оригінал використовує три socket.io-сервери (notify/log/chat). Наш план:

- **Етап 1 (MVP)**: без реалтайму; сповіщення підтягуються при синхронізації.
- **Етап 2**: WS-релей на бекенді — один канал клієнт↔ми, всередині ми тримаємо
  socket.io-підключення до notify/chat MyStat і транслюємо події
  (`socket_notification`, `socket.incoming.message`, лічильники) у наш протокол.
- Лог-сокет (трекінг активності `u_tta`) — **не відтворюємо** (нам не потрібно
  імітувати активність; чесність важливіша).

## 🚢 Деплой і порти

Розробка — повністю на localhost:

| Сервіс | Dev-адреса |
|---|---|
| Фронтенд (SvelteKit dev) | `http://localhost:5173` |
| Бекенд (uvicorn) | `http://127.0.0.1:8080` ⚠️ 8000 зайнятий старим мок-сервером MyStat з кореня проєкту |
| Swagger бекенда | `http://127.0.0.1:8080/docs` |

Дев-перевірка зв'язки однією командою: `powershell -File scripts\dev_check.ps1`.

Прод (`m1id.xyz`, за потреби додамо піддомени):

```
m1id.xyz  ──Caddy/nginx (TLS, авто-сертифікати)
   ├── /                → статика PWA (adapter-static, віддається веб-сервером)
   ├── /api/*           → reverse_proxy → 127.0.0.1:8000   (FastAPI)
   └── SPEC_URL бека    → при старті тягне свіжий openapi.json
```

Порт бекенда на проді: **8000** (слухає лише 127.0.0.1, назовні — лише через
reverse-proxy). Якщо зайнятий — міняємо в одному місці `.env`.

  спінерів, pull-to-refresh з «аврорним» індикатором.
- **Моменти**: онбординг-анімація («Привіт 👋 …») в тій же стилістиці;
